# نگهداری مخزن و انتشار PinHarbor

این راهنما مخصوص مالک مخزن GitHub است؛ کاربران عادی فقط به README و Releases نیاز دارند.

## ۱. به‌روزرسانی مخزن قبلی (از ۲.۵ به ۲.۵.۱)

1. از پوشه فعلی پروژه که `.git` دارد یک کپی پشتیبان تهیه کنید؛ از پوشه تصاویر دانلودشده جدا نگهش دارید.
2. بسته **GitHub Repository v2.6.0** را استخراج کنید. فایل‌های داخل آن را **روی محتویات پوشه قبلی** کپی و Replace کنید؛ پوشه `.git` قبلی را حذف یا جایگزین نکنید.
3. `Publish to GitHub.bat` را داخل همان پوشه قبلی اجرا کنید. مخزن `pinharbor` را وارد کنید و قبل از تأیید، حساب GitHub را بررسی کنید.
4. اسکریپت فقط فایل‌های مجاز را Stage می‌کند و موارد اضافی شناخته‌شده نسخه ۲.۵ را **از Git خارج می‌کند** (`git rm --cached`)؛ فایل‌ها روی کامپیوتر پاک نمی‌شوند. فایل‌های ناشناس یا شخصی حذف نمی‌شوند.
5. عبارت `PUBLISH` را برای ارسال Commit جدید وارد کنید. بعد در GitHub شاخه `main`، README و تب Actions را بررسی کنید.

**مهم:** بسته را در یک پوشه جدید اجرا نکنید اگر مخزن `pinharbor` قبلاً ساخته شده؛ در آن صورت ممکن است ابزار تلاش کند مخزن تکراری بسازد. همان پوشه دارای `.git` را به‌روزرسانی کنید. اگر مخزن را قبلاً Clone کرده‌اید، روی همان Clone کار کنید.

برای بررسی بدون ارسال:

```powershell
python tools/github_publish.py --repo pinharbor
python tools/verify_repository.py
python -m unittest discover -s tests -v
```

اگر در خروجی خطایی درباره «staged unrelated files» دیدید، قبل از ادامه تغییرات Stageشده دیگر را جداگانه مدیریت کنید؛ ابزار عمداً آن‌ها را Commit نمی‌کند.

## ۲. ساخت نسخه اجرایی و فایل‌های دانلود

GitHub Actions هنگام Push به `main` تست و ساخت ویندوز را اجرا می‌کند. اگر موفق شد، ZIP اجرایی را از **Actions → Artifacts** بگیرید و روی یک سیستم ویندوز تست کنید. تا قبل از آزمون واقعی، به محصول برچسب Stable نزنید.

برای ایجاد Release پیش‌نویس، پس از تأیید تست‌های دستی:

```powershell
git tag -a v2.6.0 -m "PinHarbor 2.6.0 beta"
git push origin v2.6.0
```

Tag فقط وقتی زده شود که مقدار `APP_VERSION` در `studio_core.py` دقیقاً `2.6.0` باشد. گردش‌کار در صورت موفقیت یک Draft Release می‌سازد و فقط فایل‌های `Windows-portable.zip`، `source.zip`، `update.zip` و `SHA256SUMS.txt` را اضافه می‌کند. آن را **خودتان** پس از بازبینی منتشر کنید (ترجیحاً ابتدا Pre-release).

## ۳. هر نسخه چه فایل‌هایی نیاز دارد؟

- `README.md` و `README-FA.md` برای صفحه اول؛ از ایجاد READMEهای تکراری خودداری کنید.
- `.github/workflows/ci.yml` و فرم‌های Issue برای تست و ارتباط کاربران.
- `tools/build_release.py` برای ساخت بسته‌های Release؛ `release_manifest.py` فهرست مجاز فایل‌ها را مشخص می‌کند.
- `docs/RELEASE-CHECKLIST.md` برای تأیید نهایی قبل از انتشار.

پوشه‌های `release/`، `dist/`، `build/`، `__pycache__/`، آرشیو SQLite، کوکی‌ها و رسانه‌های دانلودشده **نباید وارد Git شوند**. فایل‌های خروجی فقط در Release/Artifacts قرار می‌گیرند. به‌دلیل مجوزهای وابستگی، انتشار EXE علاوه بر تست فنی به بازبینی تعهدات مجوزها نیاز دارد.
